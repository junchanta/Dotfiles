# catch-up

対象：$ARGUMENTS

対象が指定されていなければ、現在のブランチと、このセッションの会話を対象にする。
「特に○○の流れ」のように重心が指定されていれば、流れの節をそこに合わせる。

しばらく離れていた本人が、一枚読めば作業に戻れる HTML artifact を作る。
コードは変更しない。コミットもしない。読むだけの作業である。

## 読み手は本人である

読み手は、この作業を自分で進めていた人である。領域も設計も知っている。失っているのは糸だけである。

- どこまで終わっていて、何が未コミットか
- いま作っている仕組みが、全体としてどう流れるのか。各段がコードのどこにあるか
- 途中で何を決め、何を覆したか
- 自分が返事をしていないせいで止まっているのは何か

したがって、領域の基礎や語彙は説明しない。初見の人向けの解説は eli-junior の役割である。
本 skill が足すのは「現在の状態」と「実物の場所」であり、どちらも会話の記憶ではなく実物から取る。

## 事実は書く直前に取り直す

長いセッションや圧縮された要約は、途中で覆った決定や、その後に動いた行番号を含んでいる。
記憶から書くと、それらしく読めるが開くと違う場所を指すページになる。読み手が一度そこで裏切られると、ページ全体を信用できなくなる。

- **コードの状態は git を正とする**。`git log <base>..HEAD`、`git status`、`git stash list`、base からの遅れを確認する。
- **行番号は `grep -n` で取る**。流れに載せるすべての場所について、書く直前に取得する。推測で書かない。
- **決定と判断待ちは会話、メモリ、設計メモ、チケットから取る**。ただし実物と食い違えば実物を正とし、食い違いをページに書く。
- **検証の状態は結果と時点を書く**。tsc、lint、テストが最後に通ったのはいつの状態か。安く回せるなら回し直す。回していないなら「未確認」と書く。
- 情報源に当たれなかった項目は空欄にせず、「確認できなかった」と書く。

集める作業は互いに独立なので、まとめて並列に走らせる。

| 知りたいこと | 取る先 |
|---|---|
| 段階と状態 | 計画（会話、設計メモ、チケット）と `git log` の突き合わせ |
| 未コミットの変更 | `git status --short`。無関係なローカル変更は分けて示す |
| 退避したもの | `git stash list`、untracked の設計メモ |
| 流れの各段の場所 | 対象ファイルへの `grep -n`（定義、呼び出し、分岐の入口） |
| 決めたこと、覆したこと | 会話、メモリ、チケットのコメント |
| 判断待ち | 会話の中で、自分が質問して返事をもらっていない点 |
| 他リポジトリや他者への依頼 | チケットのコメント、引き継ぎメモ |

## ページに置く節

次の順に置く。上から読んで途中でやめても、やめた地点までで役に立つ順である。

1. **ヘッダー**：チケット、リポジトリとブランチ、日付。行番号がどの状態のものか（未コミット分を含むか）を一文で書く
2. **現在地**：段階の表。列は段階、内容、状態、コミット。状態の語は「済」「未コミット」「未着手」「保留」に固定し、色つきの小さな札で示す。表の前に、どこまで終わって何を待っているかを二文か三文で述べる。検証の状態もここに書く
3. **処理の流れ**：いま作っている仕組みを、データか制御が通る順に四つから八つの段で示す。このページの中心である。書き方は次節
4. **形や語の対応**：同じものが段によって別の形や名前を取るなら、対応表を一つ置く。無ければ置かない
5. **その領域に固有の図**：形状、状態遷移、画面の部位など、図にしたほうが早いものがあれば一つ置く。飾りの図は置かない
6. **判断待ちと未コミットの変更**：自分の返事待ちで止まっている点を箇条書きにする。未コミットのファイル一覧と、触っていないもの（無関係なローカル変更、stash、放置している旧実装）を添える

決めたことと覆したことは、独立した節にせず、関係する段の説明の中に書く。流れから離れた決定の一覧は読まれない。

### 処理の流れの書き方

一つの段は次の要素で組む。

- **見出し**：その段で起きることを動詞で書く（「現在のスタイルを読む」「検査し、違反は差し戻す」）。未完成の段には状態の札を付ける
- **本文**：何を受け取り、何をして、何を渡すか。三文から五文。途中で決めた規則や覆した判断があれば、理由を一文添えてここに書く
- **例**：段の境界でデータの形が変わるなら、短い実例を一つ置く。読む必要のある行だけに絞る
- **該当箇所**：ファイルごとにまとめる。パスはリポジトリ相対のフルパスを一度だけ等幅で書き、その下に `:行番号` と、その行に何があるかを並べる

該当箇所は、読み手がエディタでそのまま開ける形にする。略記したパスや、行番号のない参照は置かない。
新規ファイルには「新規」と添える。他リポジトリや外部（チケットのコメントなど）にある場合は、その所在を書く。

まだ実装していない段も流れに含める。「ここは未対応で、いまはこう振る舞う」と書く。未完成の段を省くと、読み手は全体が動くものと誤解する。

## artifact の作り方

書く前に `artifact-design` skill をロードする。図を描くなら `artifact-diagramming` も併せてロードする。
HTML を scratchpad に書き、`Artifact` ツールで公開して URL を返す。公開できない環境では、HTML のパスを返す。

- 日本語で書く。文体はユーザーの指定に従う
- 道具としての文書であり、派手な冒頭は要らない。現在地の表までを最初の一画面に収める
- 流れは縦の連なりとして組み、段の番号は実際の順序を表すときだけ付ける
- パスと行番号、コミットのハッシュ、識別子は等幅にする。長いパスは折り返せるようにする
- ローカルファイルへはリンクできないので、リンクにしない
- ライトとダークの両方で読めるようにする

## 会話への返信

artifact を公開したら、会話には短く返す。

1. URL
2. ページに何が載っているかを節ごとに一行ずつ
3. ページを読む前に知っておくべき注意（行番号の時点、未完成の段）
4. 判断待ちの一覧。ページと同じ内容を、ここにも書く。読み手が最初に返せるのはこれだからである

コードを変更していないことを一言添える。

## 納品前の点検

- [ ] 行番号をすべて `grep -n` で取り直した。未コミット分を含むかどうかをヘッダーに書いた
- [ ] 段階の状態が `git log` と `git status` に一致している。コミットのハッシュが実在する
- [ ] 流れに未完成の段が含まれており、現在の振る舞いが書いてある
- [ ] 各段の該当箇所が、フルパスと行番号と「そこに何があるか」の三点でそろっている
- [ ] 会話の途中で覆った決定が、古いほうのまま載っていない
- [ ] 判断待ちが、ページと会話への返信の両方に載っている
- [ ] 無関係なローカル変更と退避物を、作業の変更と分けて示した
- [ ] 領域の基礎の説明で紙幅を使っていない
- [ ] コードを変更していない。コミットしていない
